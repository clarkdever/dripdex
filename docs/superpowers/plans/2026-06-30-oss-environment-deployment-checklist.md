# OSS Environment And Deployment Checklist

Date: 2026-06-30
Status: Deployment checklist for future OSS/self-host implementation
Issue: #35 Task: Create OSS Environment And Deployment Checklist

## Goal

Capture the low-infrastructure deployment path for the open-source, single-owner DripDex edition before implementation assumptions drift.

This checklist is intentionally conservative. It documents the target operating shape and the environment contract DripDex should grow toward; it does not claim all variables or adapters are implemented today.

## Deployment Profiles

| Profile | Purpose | Data shape | Fit for MVP |
|---|---|---|---|
| OSS single-owner | Parent, teacher, hobbyist, or local club self-hosts one journal. | SQLite-first data, configurable auth, configurable image storage, owner-only private workflows. | Primary open-source target. |
| Static/demo preview | Public browsing and fixture-backed demo without owner uploads. | Fixture data and public web derivatives only. | Good for public previews and docs screenshots. |
| Managed SaaS future | Hosted multi-user product with convenience features. | Postgres/PostGIS, managed auth, managed storage, usage controls, backups, billing. | Out of scope for this checklist. |


## Environment Variables

Do not commit real secrets to the repo, fixture files, docs, issue comments, screenshots, or PR descriptions. Use host-level secret storage or a local `.env` file that is ignored by git.

### Currently Consumed

| Variable | Required | Purpose | Safe example |
|---|---:|---|---|
| `DRIPDEX_OWNER_USERNAME` | Yes for `/journal` | Single owner login username for the OSS preview. | `owner` |
| `DRIPDEX_OWNER_PASSWORD_HASH` | Yes for `/journal` | Scrypt password verifier generated with `npm run owner:hash`. | `scrypt$v1$...` |
| `DRIPDEX_AUTH_SECRET` | Yes for `/journal` | Session signing secret generated by the owner or host. | `openssl rand -base64 48` |

### Planned Before Real Owner Uploads

These names are the intended deployment contract. Implementation issues may refine them, but they should preserve the same boundaries.

| Variable | Required before real use | Purpose | Secret? | Sensitive? |
|---|---:|---|---:|---:|
| `DRIPDEX_PUBLIC_BASE_URL` | Yes | Canonical public URL for links, callbacks, and docs references. | No | No |
| `DRIPDEX_OWNER_USERNAME` | Yes | Single owner login identity for OSS mode. | No | Yes |
| `DRIPDEX_OWNER_PASSWORD_HASH` | Yes | Scrypt password verifier for the owner account. | Yes | Yes |

Secret handling rules:

- Generate secrets with a cryptographically strong password manager or host secret generator.
- Rotate secrets after accidental exposure.
- Never use placeholder real-looking API keys in docs.
- Never print secrets in build logs, test output, screenshots, or handoff comments.
- Treat sensitive non-secret values as private operational data. Owner username, private storage roots, database locations, private map tile URLs, and tile provider tokens must stay out of screenshots, public issues, public sample env files, and logs.

## SQLite Persistence

SQLite is the preferred open-source default because a single-owner field journal should not require managed database infrastructure.

SQLite assumptions:

- SQLite fits the expected OSS scale: one owner, modest public traffic, and hundreds or thousands of observations rather than millions.
- The SQLite database file must live on persistent storage.
- The app should treat database backups as mandatory before real observations.
- Schema migrations should be checked into the repo once database writes are implemented.
- Exact private coordinates, EXIF summaries, owner notes, and audit history belong in the private database layer, not in public fixture files.

Host guidance:

- Good fit: a small VPS, home server, NAS, classroom server, or container host with persistent volume mounts.
- Risky fit: serverless hosts without persistent writable disk.
- Vercel fit: public app/demo or serverless web tier only if SQLite is replaced by a managed database or remote persistent storage adapter.

Backup checklist:

- Back up the SQLite database file.
- Back up private originals separately from public derivatives.
- Encrypt or otherwise access-control backups that contain private originals, exact coordinates, EXIF summaries, owner notes, or owner identity.
- Define retention and deletion rules so private originals can expire from backups when the owner expects them to be gone.
- Test restore into a fresh checkout before trusting the backup plan.
- Test restore in a private environment that does not expose originals, exact coordinates, or raw EXIF to public routes.
- Keep at least one offline or provider-independent backup for family/classroom data.

## Image Storage Assumptions

DripDex separates private originals from public derivatives.

Required storage boundaries:

- Private originals may contain sensitive image context and should be owner-only.
- Public derivatives must be EXIF-stripped before serving.
- Public card/full/thumbnail derivatives can be regenerated from private originals when originals are retained.
- Synthetic EXIF test fixtures under `tests/fixtures/exif/` are for tests only and must not be published as public sample assets.
- Fixture images under `docs/fixtures/web-images/` are public sample derivatives, but still require source/license attribution.

Local/self-host filesystem layout:

```text
data/
  dripdex.sqlite
  private-images/
    originals/
  public-images/
    full/
    card/
    thumbnails/
```

Object-storage layout:

```text
private/
  originals/
public/
  full/
  card/
  thumbnails/
```

Object storage privacy rule:

- Prefixes such as `private/` and `public/` are naming conventions, not access control. Private originals must live in a private bucket/store or behind owner-authenticated signed/proxied access. Public storage is acceptable only for EXIF-stripped derivatives that are intentionally visitor-safe.

Upload boundary rules before real capture integration:

- Reject unsupported file types before decode.
- Reject oversized files before image processing.
- Canonicalize filesystem paths and verify containment with a safe relative-path check before reading or writing.
- Reject `..`, absolute user keys, URL-like user keys, and normalized paths that escape the configured storage root.
- Return storage keys or URLs to the app, not raw server filesystem paths.
- Keep public derivative generation server-side or in a trusted worker path.

## Vercel Free-Tier Caveats

Vercel can be useful for public previews, Git integration, HTTPS, and small demos. It should not be treated as the default complete OSS storage/runtime story for DripDex until persistence adapters are wired.

Current Vercel references to check before publishing deployment docs:

- Account plans: <https://vercel.com/docs/plans>
- Hobby plan: <https://vercel.com/docs/plans/hobby>
- Platform limits: <https://vercel.com/docs/limits>
- Functions: <https://vercel.com/docs/functions>
- Function limitations: <https://vercel.com/docs/functions/limitations>
- Storage overview: <https://vercel.com/docs/storage>
- Reading files in functions: <https://vercel.com/kb/guide/how-can-i-use-files-in-serverless-functions>
- Image Optimization limits and pricing: <https://vercel.com/docs/image-optimization/limits-and-pricing>

Caveats to document in future Vercel-specific setup:

- Hobby is intended for non-commercial personal use and has usage limits.
- If Hobby usage limits are exceeded, features may pause or fail rather than silently become paid.
- Runtime logs on Hobby are short-lived, so do not rely on them as the only audit trail.
- Serverless functions scale per invocation and can scale down to zero, so local process memory and local writable files should not be treated as durable state.
- Public fixture files bundled at build time are fine for demos, but owner uploads and SQLite writes need persistent storage outside the deployment bundle.
- Vercel Storage products or marketplace databases may fit some installs, but they are provider choices behind adapters, not the DripDex core architecture.
- Image Optimization has plan limits and failure modes. DripDex public derivatives are already generated by the app pipeline, so a Vercel deployment should decide deliberately whether to use Next/Vercel image optimization or serve prebuilt derivatives unoptimized.
- Build, file-count, static-upload, and function limits can change. Link to current Vercel docs instead of hardcoding fragile numbers except where a release checklist has just verified them.

## Recommended OSS Deployment Path

### Path A: Single-Owner VPS Or Home Server

Use this as the first full OSS target when real uploads and SQLite writes exist.

Checklist:

- [ ] Provision a host with Node matching `package.json`.
- [ ] Create a persistent app data directory.
- [ ] Set `DRIPDEX_DATABASE_URL` or the final SQLite path variable to a persistent disk path.
- [ ] Set private and public image storage roots to persistent disk paths.
- [ ] Configure owner auth and secrets.
- [ ] Configure AI/search providers as disabled by default.
- [ ] Run `npm install`.
- [ ] Run `npm run build`.
- [ ] Run `npm run start` behind HTTPS reverse proxy or host-managed TLS.
- [ ] Verify public browsing does not expose private coordinates or original images.
- [ ] Verify owner-only routes are unavailable without owner auth.
- [ ] Configure backups for database and image storage.

### Path B: Vercel Public Preview

Use this for fixture-backed public preview or docs-linked demo while storage/database adapters are still maturing.

Checklist:

- [ ] Deploy from GitHub integration or Vercel CLI.
- [ ] Keep owner upload/capture disabled unless persistent storage and database adapters are configured.
- [ ] Do not store SQLite or uploaded images on the serverless deployment filesystem.
- [ ] Use fixture-backed public data or an external database/storage adapter.
- [ ] Decide whether Next image optimization is enabled or derivatives are served as prebuilt public assets.
- [ ] Review current Hobby limits before sharing broadly.
- [ ] Add monitoring/alerts appropriate to the chosen plan.

### Path C: Managed SaaS Future

This is out of scope for the OSS checklist.

Future SaaS may use:

- Supabase Auth or another managed auth adapter.
- Postgres/PostGIS for multi-user data and geospatial queries.
- Managed object storage.
- Usage controls for AI and image processing.
- Backups, team roles, billing, moderation, and support workflows.

Do not make the OSS README depend on SaaS-only services.

## Pre-Launch Privacy Checklist

- [ ] No private originals are served from public routes.
- [ ] Public derivatives have no EXIF/XMP/IPTC metadata.
- [ ] Exact coordinates are owner-only.
- [ ] Public locations use stored generalized or obscured outputs.
- [ ] Home-zone and sensitive observations receive stricter public generalization.
- [ ] Guestbook submissions require owner approval before public visibility in any persistent implementation.
- [ ] AI suggestions remain owner-reviewed and cannot publish directly.
- [ ] Logs do not contain secrets, exact private coordinates, or raw EXIF dumps.
